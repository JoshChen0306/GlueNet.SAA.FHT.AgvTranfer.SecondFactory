## 1. 功能概覽

| 功能 | 觸發條件 | 核心目的 |
|------|---------|---------|
| **二樓站內運輸** | 系統偵測上料區（O/P）有需求，但下料區（Q）無空平板 | 自動回收空平板，確保生產線不中斷 |
| **AGV 自動復歸** | 跨樓層車輛閒置超過設定時間，且不在母樓層（4F） | 自動將車輛送回 4F 待命，降低跨樓層等待延遲 |
| **預派調度** | 有跨樓層任務，但車輛不在任務起點樓層 | 自動先調車到起點樓層，再執行正式任務 |

這三項功能彼此有交互關係：
- **自動復歸** 和 **預派調度** 共用同一個管理器（`CrossFloorManager`）
- **預派調度** 的任務佇列邏輯會在新任務進入時取消已在進行的歸位計時
- **站內運輸** 是獨立的二樓派送邏輯，但同樣透過 `oMission` 與 AGV 互動

## 2. 二樓站內運輸（空平板自動派送）

### 2.1 功能說明

**背景問題：**
在二樓製程中，AGV 要將物料送到上料區（O/P 站），但下料區（Q 站）必須先有空平板，否則上料完成後無處放卸下的空架。

**自動化解決方式：**
系統在產生搬運任務前，會先檢查對應下料區的空平板狀態。若發現狀態不符，自動產生「空平板回收任務」，優先處理後再繼續原本的物料派送。

### 2.2 站點角色說明

| 站點代號 | 說明 | HaveFlag 值 |
|---------|------|------------|
| O1～O8, P1～P9 | **上料區**，放置要送往機台的物料 | — |
| Q1～Q9 | **下料區**，機台卸下空平板的位置 | 0=空架 / 1=空平板 / 3=料盤 |
| M, R | **緩衝暫存區**，空平板回收的候補位置 | — |

### 2.3 判斷邏輯（四種情境）

| 上料區狀態 | 下料區狀態 | 系統行為 | 物料派送？ |
|-----------|-----------|---------|-----------|
| 無空板（HaveFlag ≠ 1） | 有空板（HaveFlag = 1） | 不需回收，直接派物料 | ✅ 立即派送 |
| 無空板（HaveFlag ≠ 1） | 無空板（HaveFlag ≠ 1） | 等待人工補料 | ❌ 暫停 |
| 有空板（HaveFlag = 1） | 已有空板（HaveFlag = 1） | 先將上料區空板送 FallbackAreas | ⏳ 等回收完成 |
| 有空板（HaveFlag = 1） | 空架（HaveFlag = 0） | 直接將空板送到下料區 | ⏳ 等回收完成 |
| 有空板（HaveFlag = 1） | 有料盤（HaveFlag = 3） | 下料區有料，無法放置，等待 | ❌ 暫停 |

> **重要：** 回收任務會以 `TaskSource = 'PLATE_RECOVERY'` 寫入 `oNeed` 表，系統下一輪才會再評估物料派送。

### 2.4 上下料區綁定設定（oPortBinding）

這是站內運輸功能的核心設定表，**每次部署或調整站點時必須維護**。

| 欄位 | 說明 | 範例 |
|------|------|------|
| `LoadingPort` | 上料區站點 | `O1`、`P1` |
| `UnloadingPort` | 對應的下料區站點 | `Q1` |
| `FallbackAreas` | 空板回收候補區域（逗號分隔，系統依序找空位） | `M,Q,R` |
| `UseFlag` | 是否啟用此綁定 | `Y` / `N` |

**現行設定範例（初始值）：**

```
O1 → Q1 (FallbackAreas: M,Q,R)
O2 → Q2 (FallbackAreas: M,Q,R)
...
P1 → Q1 (FallbackAreas: M,Q,R)
P2 → Q2 (FallbackAreas: M,Q,R)
...
```

> 可透過後台管理介面（`/PortBinding` 頁面）進行新增/修改/啟停用，無需改程式碼。

## 3. AGV 自動復歸

### 3.1 功能說明

**背景問題：**
跨樓層車輛（目前設定為車號 1）若在任務完成後停留在 1F 或 2F，下一次有 4F 任務時必須先調車，增加等待時間。

**自動化解決方式：**
車輛閒置超過設定秒數後，系統自動發出歸位任務，將車輛送回 4F 待命。

### 3.2 運作流程

```
Dispatch 主循環（每秒執行）
  └─ CrossFloorManager.Tick()
       ├─ 車輛執行中（Status=R）→ 不處理
       ├─ 車輛在 4F → 重置計時
       ├─ 車輛 IDLE + 不在 4F
       │    ├─ 尚未計時 → 啟動計時
       │    ├─ 計時中未超時 → 繼續等待
       │    └─ 計時超時 → 產生 IDLE_RETURN 任務 → 寫入 oMission
       └─ 歸位任務已派發（_idleReturnDispatched=true）→ 等待 Callback
```

### 3.3 與新任務的互動

| 情境 | 說明 | 系統行為 |
|------|------|---------|
| 計時中，新任務進入 | 車輛還沒啟動歸位 | 取消計時，直接派發新任務 |
| 歸位任務已派發，新任務進入 | 車輛已在歸位途中 | 新任務排入佇列，等歸位完成 Callback 後重新評估 |

### 3.4 設定參數（FHtSetting.config）

```xml
<AGVSettings
  CrossFloorShuttleId="1"       <!-- 指定哪一台車是跨樓層車輛 -->
  IdleReturnTimeout="300"       <!-- 閒置超過幾秒後歸位（預設 300 秒 = 5 分鐘） -->
  IdleReturnFloor="4F"          <!-- 歸位目的樓層 -->
  MapCodeFloorMapping="AA:1F,BB:2F,DD:3F,FF:4F"  <!-- MapCode 對應樓層 -->
/>
```

### 3.5 任務標記

歸位任務在 `oMission` 表中的 `TaskSource` 欄位值為 `IDLE_RETURN`，可用此欄位辨識是系統自動產生的歸位任務。

## 4. 預派調度（跨樓層預調度機制）

### 4.1 功能說明

**背景問題：**
當有跨樓層任務時，若車輛停在 2F，任務起點卻是 4F，必須先調車才能執行。若沒有管控，可能同時派多筆任務或重複調車。

**自動化解決方式：**
系統透過佇列管理，確保：
1. 同一時間只派一筆任務給跨樓層車輛
2. 同樓層任務優先於跨樓層任務
3. 必要時自動產生「空車移動任務」先送車到起點樓層

### 4.2 任務派發優先順序

```
有跨樓層待派任務時：
  1. 有系統調度任務（CROSS_FLOOR_DISPATCH）未完成 → 繼續等待
  2. 車輛有同樓層任務 → 優先派發同樓層任務
  3. 無同樓層任務，車輛不在最早任務的起點樓層 → 先產生預調度任務送車過去
  4. 車輛已到起點樓層 → 派發正式任務
```

### 4.3 情境對照表

| 情境 | 車輛狀態 | 佇列內容 | 處理方式 |
|------|---------|---------|---------|
| 車輛執行中 | 執行中（R） | — | 等任務完成 |
| 佇列空 | IDLE | 無任務 | 交由自動復歸處理 |
| 有同樓層任務 | IDLE | 含同樓層任務 | 直接派發同樓層任務 |
| 只有跨樓層任務 | IDLE | 只有跨樓層任務 | 產生 CROSS_FLOOR_DISPATCH 預調度 |
| 預調度完成 | IDLE | 有任務 | 車已到起點，派發正式任務 |
| 預調度執行中 | 執行中 | 新任務進入 | 等預調度完成後重評估 |

### 4.4 TaskType 路由設定（oTaskTypeRoute）

此表控制每個樓層方向對應到 RCS 系統的任務類型代碼，**部署時必須確認代碼與 RCS 設定一致**。

| MoveType | 說明 | FromFloor | ToFloor | TaskType |
|----------|------|-----------|---------|---------|
| `Transport` | 搬運任務（含貨） | `2F` | `2F` | `F001` |
| `Transport` | 搬運任務（含貨） | `1F` | `1F` | `F002` |
| `Transport` | 跨樓層搬運 | `2F` | `4F` | `F24Test` |
| `Transport` | 跨樓層搬運 | `4F` | `2F` | `F42Test` |
| `EmptyMove` | 空車移動（歸位/預調度） | `2F` | `4F` | `EM24` |
| `EmptyMove` | 空車移動（歸位/預調度） | `4F` | `2F` | `EM42` |
| ... | ... | ... | ... | ... |

> **TaskType 代碼必須與 RCS 系統設定完全一致，否則 AGV 會收不到任務。**

### 4.5 任務標記

預調度任務在 `oMission` 表中的 `TaskSource` 欄位值為 `CROSS_FLOOR_DISPATCH`。

## 5. 部署時資料庫異動清單

### 5.1 全新部署（首次安裝）

依序執行以下 SQL 檔案：

| 執行順序 | SQL 檔案名稱 | 說明 |
|---------|------------|------|
| 1 | `Deploy_oShuttle_AddUpdateTime.sql` | 為 oShuttle 表新增 `UpdateTime` 欄位 |
| 2 | `Deploy_oPortBinding.sql` | 建立 `oPortBinding` 表並寫入初始綁定資料 |
| 3 | `Deploy_oTaskTypeRoute.sql` | 建立 `oTaskTypeRoute` 表並寫入 TaskType 路由 |
| 4 | `Deploy_pFunction_PortBindingMenu.sql` | 新增後台選單（上下料區綁定管理） |
| 5 | `Deploy_pFunction_RouteMenu.sql` | 新增後台選單（路線管理） |
| 6 | `Deploy_pFunction_TaskTypeRouteMenu.sql` | 新增後台選單（TaskType 路由管理） |

### 5.2 程式版本更新（已有舊資料庫）

| 步驟 | 動作 | 說明 |
|------|------|------|
| 1 | **確認 oShuttle.UpdateTime 欄位是否存在** | `SELECT UpdateTime FROM oShuttle` 若報錯，執行 `Deploy_oShuttle_AddUpdateTime.sql` |
| 2 | **確認 oPortBinding 表是否存在** | 若不存在，執行 `Deploy_oPortBinding.sql` |
| 3 | **確認 oTaskTypeRoute 表是否存在** | 若不存在，執行 `Deploy_oTaskTypeRoute.sql` |
| 4 | **確認 oTaskTypeRoute 資料** | 執行 `Verify_oTaskTypeRoute.sql` 驗證各路由資料是否齊全 |
| 5 | **確認 oPortBinding 資料** | `SELECT * FROM oPortBinding` 確認站點綁定符合現場 |

### 5.3 需要手動調整的資料項目

**oPortBinding（每次現場調整站點時）**

```sql
-- 啟停用某個綁定
UPDATE oPortBinding SET UseFlag = 'N' WHERE LoadingPort = 'O1'

-- 修改回收候補區域
UPDATE oPortBinding SET FallbackAreas = 'M,Q' WHERE LoadingPort = 'O1'

-- 新增綁定
INSERT INTO oPortBinding VALUES ('O9', 'Q9', 'M,Q,R', 'Y')
```

**oTaskTypeRoute（TaskType 代碼與 RCS 確認後）**

```sql
-- 修改正式環境的 TaskType（測試代碼改為正式代碼）
UPDATE oTaskTypeRoute SET TaskType = 'F001_PROD' WHERE MoveType='Transport' AND FromFloor='2F' AND ToFloor='2F'

-- 停用不使用的路線
UPDATE oTaskTypeRoute SET UseFlag = 'N' WHERE FromFloor='1F' AND ToFloor='3F'
```

### 5.4 不需要手動修改的資料（程式自動管理）

- `oNeed`、`oRequire`、`oMission`：程式自動新增/更新
- `oShuttle`：程式每秒更新車輛狀態
- `oPort`：程式根據 AGV 回報自動更新 HaveFlag

## 6. 測試注意事項

### 6.1 測試環境啟用 TestMode

**修改 `FHtSetting.config`：**

```xml
<FHtSettings TestMode="true" ... />
```

啟用後，`PostData` HTTP 呼叫會被跳過，直接回傳 `"TestMode"`，不會發送真實請求到 FHT 系統。
**上正式環境前必須改回 `false`。**

### 6.2 二樓站內運輸測試

**前置準備：**
1. 確認 `oPortBinding` 表有正確的站點綁定資料
2. 確認 `oPort` 表中各站點 `UseFlag = 'Y'`
3. 在 `oPort` 手動設定測試站點的 `HaveFlag`（0=空架、1=空板、3=料盤）

**測試情境建議：**

| 測試情境 | oPort 設定方式 | 預期結果 |
|---------|-------------|---------|
| 正常派送（下料區有空板） | Q1.HaveFlag=1, O1.HaveFlag≠1 | 直接派物料到 O1 |
| 觸發回收（上料區有空板、下料區空架） | O1.HaveFlag=1, Q1.HaveFlag=0 | 先產生回收任務到 FallbackAreas |
| 回收到候補區（下料區已有空板） | O1.HaveFlag=1, Q1.HaveFlag=1 | 空板送 M 或 Q 的其他空位 |
| 無法派送（下料區有料盤） | Q1.HaveFlag=3 | 物料 oNeed 卡住，log 顯示等待 |

**驗證方式：**
- 觀察 `oNeed` 表是否出現 `TaskSource='PLATE_RECOVERY'` 的記錄
- 觀察 Log 中是否有 `CheckAndHandleEmptyPlateRecovery` 相關訊息
- 確認 `oMission` 任務依序產生，先有回收任務，後有物料任務

### 6.3 AGV 自動復歸測試

**前置確認：**
1. `FHtSetting.config` 中 `CrossFloorShuttleId` 設定正確車號
2. `IdleReturnTimeout` 可先設小（如 `30`）方便測試，測後記得改回
3. `MapCodeFloorMapping` 對應正確（決定車輛目前在哪個樓層）

**測試步驟：**
1. 讓跨樓層車輛執行一筆任務到非 4F 樓層
2. 任務完成後確認車輛 Status 回到 `I`（IDLE）
3. 等待超過 `IdleReturnTimeout` 秒數
4. 確認 `oMission` 表出現 `TaskSource='IDLE_RETURN'` 的任務
5. 確認車輛接受任務並移動回 4F

**注意：**
- 若車輛 `UpdateTime` 超過 60 秒未更新，`CrossFloorManager` 會視為離線，不啟動計時
- 測試前確認車輛連線狀態正常

### 6.4 預派調度測試

**前置確認：**
1. `oTaskTypeRoute` 表中 `EmptyMove` 類型的路由資料齊全
2. 對應的 TaskType 代碼在 RCS 中已設定

**測試步驟：**
1. 讓跨樓層車輛停在 2F（非任務起點）
2. 建立一筆起點為 4F 的跨樓層任務（寫入 `oMission`）
3. 觀察系統是否產生 `TaskSource='CROSS_FLOOR_DISPATCH'` 的預調度任務
4. 等預調度任務完成（車到 4F 後），確認系統接著派發正式任務

**驗證方式：**
- `oMission` 表依序出現：CROSS_FLOOR_DISPATCH → 正式任務
- Log 中出現 `SelectNextMission` 相關訊息
- 確認整個流程只派一筆任務，不會同時派兩筆給同一台車

### 6.5 通用測試注意事項

| 項目 | 說明 |
|------|------|
| **車輛 MapCode 對應** | `oShuttle.MapCode` 必須能對應到 `MapCodeFloorMapping` 設定的樓層，否則系統無法判斷車輛位置 |
| **TaskType 代碼確認** | 每次與 RCS 團隊確認 TaskType 代碼後，才可更新 `oTaskTypeRoute` 資料 |
| **一次只改一項** | 三項功能互相影響，測試時建議一次只驗證一項，避免干擾 |
| **Log 等級** | 測試時確認 Log 等級設定可輸出 DEBUG 或 TRACE 層級，方便追蹤流程 |
| **回滾方案** | 測試前備份 `oPortBinding` 和 `oTaskTypeRoute` 資料，以便快速回滾 |

## 7. 常見問題與排查

### Q1：空平板回收任務一直重複產生

**可能原因：**
- 上一筆回收任務已寫入 `oMission` 但尚未完成，系統未正確偵測到進行中任務

**排查步驟：**
```sql
-- 查詢進行中的回收任務
SELECT * FROM oMission WHERE TaskSource = 'PLATE_RECOVERY' AND OkFlag IS NULL
SELECT * FROM oRequire WHERE TaskSource = 'PLATE_RECOVERY'
SELECT * FROM oNeed WHERE TaskSource = 'PLATE_RECOVERY' AND AssignFlag = '0'
```

---

### Q2：車輛閒置很久但沒有自動歸位

**可能原因：**
1. `UpdateTime` 超過 60 秒（車輛被判定為離線）
2. `CrossFloorShuttleId` 設定錯誤
3. `MapCodeFloorMapping` 無法解析車輛的 MapCode

**排查步驟：**
```sql
-- 查詢車輛最後更新時間
SELECT ShuttleId, Status, MapCode, UpdateTime,
       DATEDIFF(SECOND, UpdateTime, GETDATE()) AS SecondsSinceUpdate
FROM oShuttle WHERE ShuttleId = '1'
```
若 `SecondsSinceUpdate > 60`，確認 AGV WebAPI 是否正常收到車輛心跳。

---

### Q3：預調度任務完成後，正式任務沒有接著派發

**可能原因：**
- Callback API 未正確回傳 `TaskSource='CROSS_FLOOR_DISPATCH'` 的完成訊號
- `_crossFloorDispatchPending` 狀態未正確重置

**排查步驟：**
1. 查看 AGV WebAPI Log，確認 `HikAGVController.AGVCallback` 有收到回調
2. 確認回調的任務 `TaskSource` 正確
3. 查看 `oMission` 中預調度任務的 `OkFlag` 是否已更新

---

### Q4：TaskType 不正確導致 RCS 拒絕任務

**排查步驟：**
```sql
-- 查詢目前所有路由設定
SELECT * FROM oTaskTypeRoute WHERE UseFlag = 'Y' ORDER BY MoveType, FromFloor, ToFloor
```
確認代碼與 RCS 管理員確認的代碼一致。

## 8. 設定檔速查

### FHtSetting.config（AGV WebAPI）

```xml
<SectionFHt>
  <FHtSettings
    WebURL="http://[IP]/API/..."
    TestMode="false"              <!-- 測試環境改 true，正式環境必須 false -->
  />
</SectionFHt>

<AGVSettings
  CrossFloorShuttleId="1"        <!-- 跨樓層車輛編號 -->
  IdleReturnTimeout="300"        <!-- 歸位計時秒數 -->
  IdleReturnFloor="4F"           <!-- 歸位目的樓層 -->
  MapCodeFloorMapping="AA:1F,BB:2F,DD:3F,FF:4F"
```
