## 最終方向（2026-07-02 確認）
- **採方案 A（完全移除 FIFO）**：B→C 選起點時，B 區所有 `HaveFlag=3` 站點全顯示，無任何先進先出限制。
- **加隱藏設定檔開關 `MyConfig:EnableB2CFifo`**：
  - **預設 `false`** → 走方案 A（放開）。
  - 設 `true` → 恢復目前 FIFO 卡控（同料號只留最早一盤）。
- **開關對客戶隱形（採方案 b）**：
  - 交付的 `appsettings.json` **不寫此 key**。`GetValue("MyConfig:EnableB2CFifo", false)` 找不到 key 直接回傳 `false`，**不丟例外**（比照現有 `ShowRackIdField` 同一 API）。
  - **只在啟用（true）時才 render `window.enableB2CFifo`**；`false`（含 key 不存在）時 cshtml 完全不輸出該變數，前端 `Dispatch.js` 以 `window.enableB2CFifo === true` 判斷。→ 網頁原始碼裡無任何開關痕跡。

## 需求說明

### 現況（已逐行讀程式碼確認）
做 B→C 時，B 區物料下拉以「料號」分組，每個料號只顯示 PutTime 最早的一盤，
其餘同料號站點被隱藏、選不到 → 即客戶說的「只能先選先到的物料」。

### 待確認的關鍵決策點（明天問客戶）
> 客戶要的是「完全不要任何先進先出限制」，還是「要能自由選批號，
> 只是不希望被同料號的其他盤擋住」？

- **若答案是前者** → 直接移除 `case "C"` 的 FIFO 過濾，B 區同料號所有 HaveFlag=3 站點全顯示。
- **若答案是後者** → 應把分組 key 從「料號」改成「批號」（或料號+批號），
  保留 FIFO 精神又不誤擋不同批號，風險更低。

## 影響評估摘要
- **正面**：同料號 B 區所有 HaveFlag=3 站點都能選。
- **風險1**：失去 FIFO 防呆 → 若有料齡/時效管控，舊料可能積壓過期，全靠人員自律。
- **風險2**：下拉變長，同料號多盤全列出，選錯盤機率上升。
- **風險3**：後端 `InsertoNeed` 本就未驗證 FIFO，移除後無任何一層擋。
- **影響範圍**：FIFO 只在 `case "C"`（1F B→C）。同函式還有 `H/M/T/MT` 等 2F case，
  改動時**不可動到共用 `workoderMap` 或其他 case**，避免誤傷 2F。
