## 二、「先進先出（FIFO）」在本系統的全貌（實證）

### 2-1 任務排隊層：純 FIFO，無優先權插隊
- `Dispatch/svrPair/cPair.cs` 全檔取任務 SQL 皆為 `order by TaskDateTime`，無 Priority 欄位：
  - oNeed：`cPair.cs:172`、`388`
  - oRequire：`cPair.cs:564`
  - oMission 指派給車：`RegisteroMissionToShuttle`（`cPair.cs:977` 附近）
- `Priority` 只用於「挑目的地 oPort 站點」（`GetoPort_*_Sort_ByBlock` 系列，`order by Priority desc`），與任務排隊無關。
- 執行模型：`DoPair()` 單執行緒、50ms 輪詢、foreach 逐筆序列處理，不並發。

### 2-2 打破 FIFO 的兩種情況
- 跨區域且前排任務所在區暫時沒車 →「就近派車、不跨區調車」，後排有車的區先做。
- 同區多筆但 TaskDateTime 完全相同 → 排序 SQL 無 tie-breaker。
  但 oNeed 的 TaskDateTime 由 Web 以 `DateTime.Now.ToString("yyyyMMddHHmmssffffff")`（微秒級）寫入
  （`DispatchController.cs:243`），實務上撞號幾乎不可能，此風險可忽略。

## 三、B→C 先進先出卡控（客戶要移除的功能）

### 3-1 位置與邏輯（實證）
- 檔案：`WebGui/SCP/wwwroot/js/Dispatch.js` → `filterBeginStationOptions()` 的 `case "C"`（約 1595-1640 行）。
- 觸發：操作員在平板/Web 選「送到 C 區」時，篩選「起點（B 區物料）」下拉。
- 核心程式：
  ```js
  var workorder = station.workOrder.split("^")[3];  // 料號（第4段）
  var lot       = station.workOrder.split("^")[2];  // 批號（第3段，僅顯示）
  var puttime   = station.putTime;                  // 放料時間

  if (tracname.startsWith("B") && haveflag === "3") {
      // 同一「料號」只保留 puttime 最早的那筆
      if (!workoderMap.has(workorder) || puttime < workoderMap.get(workorder).puttime) {
          workoderMap.set(workorder, { tracname, lot, puttime });
      }
  }
  // .each()：是該料號 puttime 最早者 → .show()（可選）；否則 .hide()（選不到）
  ```
- 顯示格式：`站號-料號-批號`。

### 3-2 關鍵事實
- **分組單位是「料號」（PartNo, index[3]），不是批號（lot, index[2]）**。
- PutTime：`DispatchController.RegisterLot(:557)` 以 `yyyyMMddHHmmssffffff` 寫入、`ClearLot(:607)` 清空。
  固定寬度字串，字串比大小 = 時間先後，比較正確（早 = 字串較小 = 保留）。
- 純 UI 層卡控（靠 `.hide()` 隱藏選項），後端 `InsertoNeed` 未再驗證 FIFO。

### 3-3 為何此功能在前端、不在 svrPair
- 本廠 `Dispatch/Release/Recipe.ini` 為 `PanelDoB2C=T`（第 4 行）、`UnloadAuto=T`（第 5 行）。
- 故 `cPair.cs:118-120` 的自動 B→C 配對 `GenerateoNeedDataByMCSAsBtoC()`（`order by Priority desc` 權重路徑）**不執行**，
  B→C 完全由平板/Web 人工操作，卡控因此寫在前端 `Dispatch.js`。

## 四、移除的影響評估

| 面向 | 影響 |
|------|------|
| 操作面（正面，客戶要的） | 同料號 B 區所有 HaveFlag=3 站點都能選，可自由挑盤送 C。 |
| 失去 FIFO 防呆（風險） | 若現場有料齡/時效管控（膠料/材料放太久失效、過期、堆積），移除後無系統防呆，全靠人員自律。 |
| 下拉選單變長（操作風險） | 同料號多盤全列出，選錯盤機率上升。 |
| 後端無補強 | `InsertoNeed` 本就未驗證 FIFO，移除後無任何一層擋。 |
| 影響範圍（要小心） | FIFO 只在 `case "C"`（1F B→C）。同函式尚有 `H/M/T/MT` 等 2F case，改動不可動到共用 `workoderMap` 或其他 case。 |

## 五、客戶為何想移除的推測

### 最強懷疑（中高信心，有程式碼依據）
分組 key 是「料號」不是「批號」。同料號在 B 區可能同時有多個批號料盤，
FIFO 只留該料號 puttime 最早一盤，導致**其他批號被隱藏、操作員想出的特定批號選不到**。
→ 真正痛點可能是「FIFO 分組單位用錯（該用批號卻用料號）」，而非「有 FIFO」本身。

### 其他可能（低信心，待確認）
- PutTime 不準（補登/清帳造成「最早」判斷錯）。
- 急單/插單想出非最早那盤。

## 六、明天要問客戶的關鍵決策點

> 客戶要的是「完全不要任何先進先出限制」，還是「要能自由選批號，只是不希望被同料號其他盤擋住」？

- 若前者 → 直接移除 `case "C"` 的 FIFO 過濾，全部顯示。
- 若後者 → 分組 key 由「料號」改「批號」（或料號+批號），保留 FIFO 又不誤擋，風險更低。

**方向確定後**再補 `spec.md` 驗收標準並開始實作，避免方向寫錯。
