# 回放報告：2026-04-21 14:32:35 預調度重複派發事件

## 事件摘要

- **時間**：2026-04-21 14:32:35
- **車輛**：20106（`CrossFloorShuttleId = 3`）
- **父任務**：MCS TaskDateTime = `20260421143048764861`
- **現象**：預調度任務完成後約 0.5 秒，系統對同一個 MCS 父任務再次派出預調度

---

## 原始失效鏈（Before Fix）

```
時刻 t0
  callback=end 抵達 DD（3F 客貨梯等待點）
  → CallBackAPI.UpdateEnd 僅更新 oShuttleStation（MapCode 不變）
  → CrossFloorManager.OnCrossFloorDispatchCompleted()  // 無參數

時刻 t0 + ~200ms
  UpdateAGVStatus 輪詢（週期性覆寫 oShuttle.MapCode）
  → 若此時 AGV 回報封包仍帶 pod/edge 上殘留的舊 MapCode（如 AA=1F）
  → oShuttle.MapCode 被覆寫為 AA

時刻 t0 + ~500ms
  Dispatch 主循環 Tick → SelectNextMission
  → GetShuttleStatus().MapCode = AA = 1F
  → triggerTask 起點 DD = 3F
  → 判斷「不同樓層 → 需派預調度」
  → 派出新的 CROSS_FLOOR_DISPATCH（parent = 20260421143048764861）
  → 重複派發
```

**核心問題**：
1. callback end 帶的 `mapCode=DD` 沒有被用來即時糾正 `oShuttle.MapCode`。
2. 記憶體沒有「剛派過同一 parent 的預調度」的記錄，因此無法攔截重派。

---

## 修復後失效路徑（After Fix）

```
時刻 t0
  callback=end 抵達 DD，帶 mapCode=DD
  → CallBackAPI.AGVCallback 抽出 sMapCode = "DD"
  → UpdateEnd(oMission, ubActivation, sCurrentPositionCode, sMapCode="DD")
    → UpdateShuttleMapCodeFromCallback → SQL Update_oShuttleMapCode  // 方案 A 關鍵
    → oShuttle.MapCode = DD（3F）✓
  → CrossFloorManager.OnCrossFloorDispatchCompleted(oMission)
    → mission.ParentTaskDateTime = "20260421143048764861"
    → CooldownTracker.RecordCompletion("20260421143048764861")      // 方案 C 關鍵

時刻 t0 + ~200ms（即使 UpdateAGVStatus 又把 MapCode 覆蓋為 AA）
  oShuttle.MapCode = AA = 1F（假設最糟情況）

時刻 t0 + ~500ms
  Dispatch 主循環 Tick → SelectNextMission
  → DecideNextCrossFloorAction(crossFloorPending, "1F", _pathCalculator, _cooldownTracker)
  → 遍歷 pending：triggerTask.TaskDateTime = "20260421143048764861"
  → cooldown.IsInCooldown("20260421143048764861") = true（<30 秒 + parent 相符）
  → 回傳 CrossFloorDecision.CooldownHit(triggerTask)
  → SelectNextMission 回傳 triggerTask（父任務本身）
  → 不呼叫 DispatchCrossFloor，不寫新 oMission        // 重派被攔截
```

**雙層保護**：
- **第一層（方案 A）**：callback 帶的 mapCode 即時寫入 oShuttle，縮短被覆蓋的窗口（最佳情況下不會觸發冷卻期機制，因為 MapCode 就是正確的）。
- **第二層（方案 C）**：就算 UpdateAGVStatus 輪詢仍覆蓋了 MapCode，冷卻期機制仍會攔截 30 秒內同一 parent 的預調度。
- **啟動復原（Task 5）**：ACC 重啟時若上次預調度才剛完成，從 ubMission 重建冷卻狀態，避免重啟後立即重派。

## 驗收標準逐項對照

> 對照 spec.md「驗收標準」區段（Given-When-Then + 條列混合）

### 方案 A（MapCode 即時更新）

- ✅ Given callback end 帶 mapCode=DD，When 抵達終點，Then `oShuttle.MapCode` 變 DD
  → `CallBackAPI.cs` AGVCallback 在 end 分支呼叫 `UpdateShuttleMapCodeFromCallback`
- ✅ Given callback cancel 帶 mapCode=FF，When 取消，Then `oShuttle.MapCode` 變 FF
  → cancel 分支同樣呼叫 `UpdateShuttleMapCodeFromCallback`
- ✅ Given callback 帶空字串 mapCode，When 抵達/取消，Then `oShuttle.MapCode` 不變動
  → `UpdateShuttleMapCodeFromCallback` 開頭 `string.IsNullOrEmpty` guard

### 方案 C（冷卻期）

- ✅ Given 剛完成預調度（parent=P1），When 30 秒內出現需派預調度的同一 parent 任務，Then 回傳該父任務（不重派）
  → `DecideNextCrossFloorAction` 內 `cooldownTracker.IsInCooldown(triggerTask.TaskDateTime)` 命中 → 回傳 `CooldownHit`
- ✅ Given 剛完成預調度（parent=P1），When 30 秒內出現不同 parent 的需派任務，Then 照常派預調度
  → IsInCooldown 匹配 parent；不同 parent 直接 false
- ✅ Given 未完成任何預調度，When 出現需派預調度任務，Then 照常派預調度
  → CooldownTracker 初始狀態 `_completedAt == null` → IsInCooldown false
- ✅ Given 31 秒前完成的預調度（parent=P1），When 出現同一 parent 任務，Then 照常派預調度（過期）
  → CooldownTracker 以 `_nowProvider` - `_completedAt` 比對秒數

### Task 5 啟動復原

- ✅ ubMission 有相符記錄 → 冷卻期欄位填入
  → `RebuildCooldownFromHistory` 成功路徑 → `Initialize`
- ✅ ubMission 無相符記錄 → 欄位維持初始值
  → `if (recent == null) return;`
- ✅ 查詢失敗 → log WARN + 維持初始值，不中斷啟動
  → `try/catch (Exception ex)` + TraceOut

## 上線風險與觀測點

### 風險

1. **冷卻期太短 / 太長**：預設 30 秒，若生產環境抵達→回派週期超過 30 秒仍可能漏網；太長則延遲合法重派。**可調**：建構子 `crossFloorCooldownSeconds` 參數。
2. **單欄位冷卻僅存最新一筆**：若同一秒連續完成兩個不同 parent 的預調度，後一筆會覆蓋前一筆。單車情境可接受（單車不可能同時有兩個預調度）。
3. **UpdateAGVStatus 仍可能覆蓋 MapCode**：方案 A 僅縮短窗口，不根治 AGV 封包汙染問題。方案 C 是最後防線。

### 觀測點（Log 關鍵字）

- `[CrossFloor] RebuildCooldown 成功` → 啟動時復原成功
- `[CrossFloor] RebuildCooldown 失敗` → SQL 例外或格式錯誤，觀察 `ex.Message`
- `[CrossFloor] 冷卻期命中` → 攔截成功（需於 `CrossFloorManager.cs` 確認有此 log）
- `[CallBack] UpdateShuttleMapCodeFromCallback WARN` → mapCode 寫入 SQL 失敗（不中斷流程）

## 結論

事件主因為「callback 帶的 mapCode 未即時寫入」+「無冷卻期記錄」雙因素造成。方案 A + C 以互補方式解決：A 縮短窗口，C 兜底攔截，Task 5 補齊重啟復原。全量 103 測試通過、0 error build，整體 4 道 Gate 全綠。建議上線後觀察首週 log 中「冷卻期命中」次數與 MapCode 抖動頻率，評估是否需調整冷卻期長度。
