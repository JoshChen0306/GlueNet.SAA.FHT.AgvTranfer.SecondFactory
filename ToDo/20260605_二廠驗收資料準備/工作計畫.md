## 核心原則

- 以現有手冊為底稿，補上二廠新增客製功能，詳細度停在「架構層級」。
- **派送 / 路由內容一律以程式碼為權威**（使用者鐵律），不可依記憶 / 計畫文件 / SQL 臆測。
- 格式 Markdown + Mermaid，沿用現有手冊風格，定稿後可轉 docx。

---

## 涵蓋的新增功能（已確認清單）

1. 二樓站內運輸（空平板自動派送）
2. AGV 自動復歸
3. 預派調度（跨樓層預調度機制）
4. 跨樓層電梯換乘
5. 跨樓層任務取消後自動重建
6. 空平板取消連動清源頭
7. 派送路由 / 路線權限（站點 → 可派終點）

D4 建置手冊 → D2 路由表 → D1 架構 → D3 流程圖 → D5 操作手冊 → D6 UML（需讀碼最多，最後）。

## 單一任務完成 4 道 Gate

每個子任務完成、標記 `[x]` 之前必須全部通過：

| Gate | 檢查項 | 判定 |
|------|--------|------|
| 1. Build | 對應專案建置 | 0 error（warning 允許） |
| 2. Test | TDD: 對應測試 / 一般: 回歸測試 | 全部通過 |
| 3. Acceptance | 逐項核對 spec.md 對應驗收標準 | 全部滿足 |
| 4. Regression | 若屬重構 / 效能優化 | 完整測試套件 0 失敗 |

任一 Gate 失敗 → 標 `[!] 阻塞中` + 停下找使用者，不得跳過。

> **文件型任務 Gate 適配說明：** 本計畫無程式碼變更，Gate 1/2/4 對應調整為「文件可正確渲染（Mermaid 圖無語法錯）+ 內含程式碼/路由敘述均已對照實際 code path 行號」；Gate 3 仍逐項核對 spec.md 驗收標準。

## 跨優先順序驗證點

### 🚦 驗證點 #1：P1 → P2（在進入第一個 P2 任務前執行）

完成的 P1 任務：T1（建置手冊）、T2（路由表）、T3（系統架構）

驗證步驟：
1. 核對 T2 路由表所有「站點→終點」敘述皆有對照的程式碼位置（DispatchController / cPair / ACC），無一處出自記憶或 SQL 臆測。
2. 核對 T1 建置手冊的 Deploy SQL 順序與 config 設定項與現行檔案一致。
3. 抽查 T3 架構圖三系統邊界與實際專案結構（SCP / Dispatch / ACC）相符，CrossFloorManager 標於 ACC。

通過 → 進入 P2 任務
失敗 → 停下找使用者討論修復方案，修復後再進入 P2
